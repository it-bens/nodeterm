# Context link

Context Link lets one agent node read another node's context on demand (pull, not push): context bridges between agent nodes, one-way links, and sticky-note links. Code: `src/core/context-link.ts`, `core/context-link-render.ts`, `renderer/lib/noteLink.ts`, `shared/canvas-link.ts`, `useContextLinkSync`. The `link` canvas-control verb that creates bridges is in [canvas control](canvas-control.md).

## What it is

A node action gated by `CONTEXT_LINK_CAPABLE` (claude, codex, gemini, opencode, grok; custom agents and plain terminals excluded; copilot is the one builtin outside it). Grok joined because its readable conversation is `chat_history.jsonl`, not the `updates.jsonl` its own hook payloads advertise. Routing through the advertised path does not error: it opens a real file, parses nothing, and hands the linked agent an empty transcript with no diagnostic (`core/handoff/locate.ts` pins it). Drawing an edge between two builtin-agent nodes lets each read the other's context on demand.

## Architecture (SSH-capable, see [SSH agent skills](ssh-agent-skills.md))

- The **desktop does the reading and the parsing**. The CLI the agent runs (`context.sh`) is a thin POSIX sh+curl shim that POSTs to the hook server's `/context-link/<verb>` route and prints the text/plain reply (the Electron-as-Node CLI is retired). Its embedded-JS parser now lives as tested TS in `core/context-link-render.ts`: parsers for all four formats (claude JSONL, codex rollout, gemini event-sourced chat, opencode export) plus `renderContextLink` over injected fetchers.
- `src/core/context-link.ts` holds the link docs in memory (per-node files under `<userData>/context-links/` remain as a debug aid), carries per-entry `agentId` / `sessionId` / `accountId`, and answers the route.
- **Authorization** = the doc is selected by the requester's node id, so a token-holding caller can only read nodes in its own (directional) link map.
- Codex and gemini paths resolve via the handoff locators (`locateCodex` / `locateGemini` by sessionId); claude keeps the hook-fed path plus `locateClaude(sessionId, accountId)` fallback (cwd-newest is claude-only).
- **Publication.** Context-link maps authorize reads, so publish changes to edges, linked metadata and background projects independently of canvas geometry updates: a debounce reset by every node render can starve publication indefinitely.
  - `useContextLinkSync` publishes semantic map changes from live edges and subscribes to background project/status changes. Geometry and status render churn cannot postpone publication.
  - Core coalesces renderer updates before workspace-map construction with a non-resetting task.
  - Only merge projects owned by the same core; relay-bound projects never enter the local core's map.
  - A render-captured project epoch prevents outgoing live nodes replacing the incoming project's persisted map during a tab switch.
  - Core replaces the read authorization map synchronously, then enriches and writes debug documents through a recoverable serialized queue. Revision checks prevent obsolete enrichment restoring a removed link: core must revoke removed links before asynchronous transcript discovery or debug-file writes finish, and an older write must never restore that access. Transcript paths can be temporarily unavailable while the current snapshot is enriched.
  - Intermediate ACL publications retain previously resolved paths keyed by node, agent, session, account, cwd, remote/local placement and hook path. Ingest prunes changed or removed identities, so changing back during queued discovery cannot revive an invalidated path; changing a session/account/location/hook path or removing the target invalidates that cache immediately. Reinitialization clears the cache, and only current-revision discovery may refill it.
- **SSH projects.** The shim and skill are installed on the remote host at connect (`RemoteHooks.installContextLink`, gated on the verified reverse hook tunnel; POSTs ride `--unix-socket` through it). A remote node's transcript is read over the ControlMaster (`initContextLink(ptyManager, deps)`: `src/main` injects `isRemoteNode` / `readRemoteFile` / `runRemoteCommand`, bounded tail reads). Its hook-fed path is jailed at ingest (`isSafeRemoteTranscriptPath`), and `resolveLinkTranscript` refuses the local locators for remote nodes (they would resolve a stranger's local transcript).
- **Server Edition** is wired (`src/server/context-link.ts` calls `initContextLink(ptyManager, {})`) but passes no remote deps, so it is local-only, which is complete there: that shell runs on the host whose transcripts and tmux it reads, and SSH projects are a desktop-only concept.
- **Discovery** is the `get-linked-context` skill in each consented context-link-capable agent's own skills dir (since #744; the old marker block `<!-- nodeterm:get-linked-context:start/end -->` in AGENTS.md / GEMINI.md is stripped, see [agent integration consent](agent-integration-consent.md)). The earlier MCP-based bridge was replaced by this.
- **Cross-project refusal.** A project-scoped lookup cannot prove a node does not exist elsewhere. Link refusals name the project boundary and explain that cross-project linking is unsupported; do not scan other projects just to improve a missing-endpoint diagnostic.

## The discovery note goes only into an empty prompt

On connect a one-line discovery note is typed into each endpoint (claude gets a skill pointer; codex and gemini get an inline CLI command via `contextLink.info()`). App-originated text goes only into an empty prompt: a note nodeterm types into an agent on its own (the context-link discovery note, a sticky pushed over a note link) goes through `linkNoteRefusal` plus `pty.sendToEmptyPrompt`, never a bare `pty.sendText`. `sendText` pastes and presses Enter, so it submits whatever the user had half-typed along with it (#1144) and answers an open permission dialog. The first version was a bare `sendText` gated only on `state !== 'working'`, so it was pasted in front of the user's half-typed draft, and a `blocked` / `waiting` pane would have had its dialog answered.

Two halves: the renderer's `linkNoteRefusal` (`renderer/lib/noteLink.ts`, the ⌘M composer's `chatSendRefusal`: never working / waiting / blocked / CLI gone) and core's `PtyManager.sendToEmptyPrompt` (`pty:send-to-empty-prompt`, both shells), which reads a styled capture with `readClaudeComposer` (`shared/agents/claude-screen.ts`) and writes only on `empty`, inside `serializePaneWrite`. Measured on Claude Code 2.1.301 (fixtures `__fixtures__/claude/composer-capture.json`): the empty composer's placeholder is SGR 2 (dim), a draft is not, shell mode (`!`) is a draft. Only dim text counts as placeholder, so a capture that lost its SGR reads `draft`, the safe direction. Emptiness is therefore provable only for an agent in `SCREEN_DIALOG_READABLE` (claude); every other agent gets no note (`unsupported`), since emptiness is read off the screen and an agent without a measured composer reader cannot be checked. A refused note is dropped, not queued: the link is the capability (pull-based), the note only advertises it, and a note arriving minutes later is the same unsolicited prompt at a moment nobody chose. Every skipped endpoint is named in one info strip (`linkNoteSkippedNotice`); a skipped note is never silent. Residual: a keystroke in the milliseconds between the capture and the write.

## One-way links (issue #852)

A context bridge may carry `reader` (`BridgeLink.reader`), the one endpoint allowed to read the other. Absent means both read, which is every pre-#852 link, so old `project.json` files load unchanged. The rule is `linkReadPairs` (`shared/canvas-link.ts`), and `buildLinkMap` is where it bites: the non-reading side gets no map entry, so main serves it no document and the resolver refuses it. Enforcement is at the read, not in the discovery note.

- A `reader` naming neither endpoint, or any present non-string value, authorizes nobody (fail closed), and is carried verbatim through every conversion: dropping it as "absent" would widen it to two-way on the next save.
- Set it from the context-link edge's right-click menu (both / A reads B / B reads A; arrowheads point at the reader; a rope drawn over a hidden link resolves it by endpoint pair via `contextLinkForEdge`) or with `link --one-way` (`--from` reads).
- On the canvas it rides `edge.data.reader`. Every bridge to edge conversion goes through `bridgeToEdge` / `edgeToBridge` (`renderer/lib/noteLink.ts`; CLI-planned bridges enter live state only via `appendBridgeEdges`), and the server merge keeps it (`serverChange.edgeRef`). A field-by-field `{id, source, target}` copy silently turns a one-way link two-way again.
- A flip that grants read access sends the same one-shot discovery note a new link sends; losing access sends nothing, like removing a link.
- The premise "every submit triggers a full read" does not hold: nothing reads on submit; the linked agent reads only when it decides to run the skill or shim. What one-way removes is the other side's permission and its discovery note.
- **Team sync carries it too.** An `edge-upsert` of kind `bridge` keeps `reader` through the diff, the shape gate, the reflector's sanitize and the peer's apply (`edgeFields` / `sameEdge` in `shared/canvas-mutations.ts`), and a flip alone is a change. A three-id copy there never cast a flip and landed a cast one-way link on the peer as both-read, which the peer then saved and published back. A malformed reader on the wire refuses the op (never dropped, since dropping widens), and a rope never carries one.

## Note links

A sticky note can be connected to any terminal node (one-way, sticky to terminal). On connect, agent sessions get a one-shot push of the note text (`buildNotePushMessage`, single-line, truncated at 2000 chars) through the same empty-prompt gate as the discovery note above; plain terminals get no push (the text would execute). The note's live text also rides the link file (`ContextLinkInfo.note`), so Claude reads the current text via the get-linked-context CLI (`summary` / `transcript` print it; `list` marks `(note)`). Pure edge/push/map logic is in `renderer/lib/noteLink.ts`.

## Related: link-creating features need an ownership rule

A feature that creates links needs an ownership rule in its plan. Verify removal on a real filesystem with real links and content. A launch-time sweep may recreate links, but must not delete a link whose ownership it cannot prove.
