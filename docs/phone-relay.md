# Phone relay (remote access)

How a paired phone reaches a desktop over the end-to-end encrypted relay: key intake and the pairing code, scoped Team Access guests, the standing host, flow control, the phone's chat and launch verbs, pins and revoke, and Windows pairing. Code lives in `src/core/relay/`, `src/main/remote/`, `src/main/pairing-core.ts` and `src/shared/remote/`. Hosted teams on the same relay are in [hosted-team-relay](hosted-team-relay.md); the phone's chat screen contract is in [mobile-chat-view](mobile-chat-view.md); the wire contracts are in [ios-protocol-migration](ios-protocol-migration.md).

## Remote access is free, not Pro

Phone relay remote access ("Reach this Mac from anywhere") is a Core (free) feature as of 2026-08-01: the iOS app is itself paid, so a desktop Pro gate charged twice for one feature. The former Pro gate and the free-tier monthly quota (`core/relay-quota.ts`, `RelayQuotaBanner`, the ProCompare meter, the `relayQuota` IPC, preload and bridge surface) were removed. The toggle (`settings.phoneAccessEnabled`, Settings → Phone and the quick-pair popover) shows for everyone, and the standing host reconciles on `enabled && relayAllowed()` alone, with no quota metering at `onPeerReady`.

Entitlement passthrough remains: a stored Pro entitlement is sent on mints, else the `{deviceId, ...}` body (host-token `{deviceId, hostPublicKeyB64}`, plus `popChallenge`/`popProof` when the backend supports it; device mint `{deviceId, hostDeviceId, hostPublicKeyB64, label}`). The backend is the real gate now: `POST /v1/relay/host-token` and `/v1/relay/device` must admit deviceId (no-entitlement) mints, and the relay server may rate-limit free hosts independently. A client-side gate must not be reintroduced to work around a backend refusal; fix the backend policy instead.

## Relay key intake: no low-order keys, one spelling per key, a 10-digit SAS

Security audit 2026-10, relay-crypto findings F1 to F5.

1. **Low-order keys are refused at one choke point.** `deriveSharedKey` (`core/relay/e2ee.ts`) refuses a peer key whose raw X25519 output is all zero (`WeakPeerKeyError`, `E_WEAK_PEER_KEY`). tweetnacl's `box.before` accepts low-order points, and with one the shared key is HSalsa20(0), a public constant: a secret-less client completed the handshake, both humans saw the same fixed SAS ("357 836"), and a 0^32 key pinned through a tampered offer or join code let anyone back in silently (`autoApprove`). Check the raw X25519 output, never `box.before`'s.
   - The host refuses in the `e2ee_hello` handler without answering and closes the socket (no throw inside the ws emit), and sets `peerPubB64` only after a successful derive, so nothing can pin or auto-approve the refused key. A client throws in `connectRelay` before dialing.
   - The other intakes are belts on that choke point: `decodeOffer`, `decodeJoinCode`, `ownerKeyProblem`, `pinDevice`/`isPinned`, and the `/pair` `epk` (400 `bad epk`). `isLowOrderPublicKey` uses a fixed probe scalar, since any clamped scalar sends exactly the low-order points to zero.
   - A peer's X25519 key always goes through `core/relay/e2ee.ts`, never straight into `nacl.box.before`. `deriveSharedKey` refuses a low-order key and `publicKeyFromB64` refuses non-canonical base64. A new intake of a key someone will pin (an offer, a code, a QR field, a pin store) validates with `peerPublicKeyFromB64` / `isUsablePeerKeyB64` and gets a `low-order-keys.test-support.ts` test.
   - Pinned by `relay-low-order.test.ts` (the audit's repro, against the real host and client).
2. **Keys and nonces must be canonical padded base64** (`canonicalB64ToBytes`). Node's decoder skips junk, so `"!!!" + key` decoded to the key, and pin stores compare strings. A join code's body is canonical base64url too, after removing ASCII whitespace (wrapped mail lines). Every producer (desktop, iOS, Android, web viewer) pads already.
3. **The SAS is v2:** `pad6(BE_u32(h[0..4]) mod 1e6) + pad4(BE_u32(h[4..8]) mod 1e4)`, shown as "NNN NNN NNNN", with h = SHA-512(shared). v1 (~20 bits) was grindable on both legs in seconds by whoever substitutes a pinned key. The first seven characters are the v1 code, and every surface shows `SAS_COMPARE_HINT` (`shared/remote/sas.ts`) under the code: the host approval dialog (`shared/remote/approval.ts`), the joiner's prompt (Canvas), the hosted owner dialog and `team status`. A new surface that shows the SAS shows the hint too. Nothing compares SAS strings in code, so mixed versions stay correct (a v1 peer shows the first six of the ten digits). Vectors are in `e2ee.test.ts` and [ios-protocol-migration](ios-protocol-migration.md) §3.1; the phones owe their own release.
4. **The host SAS dialog has one slot.** A different device's pending request is refused while one is open (`renderer/lib/pendingPeerAdmission.ts`: a phone is rejected and retries, a relay peer is never confirmed), never swapped in under the human comparing digits. The same device re-raising (#372 retry churn) replaces in place.
5. **The pairing QR carries `sshHostKeys`** (`SHA256:...` in the `ssh-keygen -lf` spelling, ordered ed25519/ecdsa/rsa, at most 4, after `relay`, before `ssh`; always omitted with `ssh:false`), so the phone pins its first SSH connect instead of trusting on first use (`main/ssh-host-key-fingerprint.ts`; phones: nodeterm-ios#75 and Android). It is complete or absent, never partial: the phones refuse a host key not in the set, and sshd presents whichever key the client's algorithm preference picks, so a missing key locks the phone out until a new QR. The set is what sshd would serve: `HostKey` lines of sshd_config plus its `Include`s (else sshd's defaults), each counted only if its private file exists (stat, never read), each `.pub` required to parse. Any doubt drops the field: an unreadable `.pub`, `HostKeyAgent`, a relative or `%`/`~` path, a glob form we do not model, more than 4 keys. An unreadable config falls back to the defaults only when all three are present and consistent. A superset is harmless.

## Team Access invites that share one project

A Team Access invite that shares one project is a boundary, not a label (`core/relay/scoped-guest-policy.ts`, wired by `main/remote/relay-host.ts` as the core relay host's hooks). The invite is consent to run commands in that project, and nothing else. A UI that hides an option is convenience; the policy in `core/relay/` is the gate.

- **Inbound is an allowlist (`SCOPED`).** A node id must belong only to the shared project, paths must realpath inside the project root and outside userData (symlinks and dangling links refused), `pty:create` loses `sshRemote` and defaults its cwd to the root, and `workspace:save` is refused. An unknown channel is refused, and the guard test forces a decision for every relay-tab channel. `connectRelayHost` throws for a scoped session given no scope deps rather than serve it unscoped.
- **Outbound** reuses the viewer policy's per-project event and terminal-frame attribution, presence included: only peers on the shared project, and no node id outside it (`createPresenceFilter`). A scoped guest's presence reaches a non-editor only for peers on its shared projects.
- **A node id the guest itself introduces over `canvas:mut` is pending, and pending unlocks nothing but its own spawn** (security audit F1, 2026-10). Such an id is one no project holds yet: the host saves on a debounce, so a new terminal's first `pty:create` precedes its node on disk. That `pty:create` carries `newOnly` (core refuses a join, a reattach, and any session that already runs under that name, `unavailable: 'new-only'`), and only that create's own `fresh: true` response makes it the guest's node. Until then every node-keyed verb and the outbound stream refuse it, even after the host saved it into the project (being on the canvas is the guest's own doing, not ownership). Introduced ids are bounded (256) and must be `[A-Za-z0-9-]` (`sessionName` rewrites anything else, so two ids could name one tmux session). The audit's attack was an SSH-project guest (no local shell granted) recording a prefix of another project's node id and reaching that local terminal through tmux prefix matching (see [tmux-continuity](tmux-continuity.md), exact tmux targets).
- **A share rooted at the disk root, the home directory, or an ancestor of either or of userData is never served** (`core/relay/share-root.ts`): every file under it would be readable, `~/.ssh` included. The invite UI shows such a project disabled with the reason (`relayHost.scopeProblems`), `addSeat` refuses to mint it, and the policy refuses every request of such a session.
- **What it does not claim:** the guest's own terminal is a shell as the host's user and can `cd` anywhere or attach another tmux session. The policy closes the app's RPC doors, not the OS.
- **Secret-bearing RPCs are host-only for every relay peer** (`shared/host-control.ts`, also enforced in core `relay-host.ts` `serve`, so the Server Edition's hosted peers meet it): `settings:*` (a peer that saved `modelGateway.baseUrl` and then called `agent:discover-models` would have the keychain-held gateway key sent to its URL), gateway credentials, `license:*`, `claude-accounts:*`/`codex-accounts:*`, `usage:*`, and the pairing and relay trust plane. An unscoped invite (Team Access seats) stays full access, and its copy says so.
- **Known degrades of the scoped tab:** the host-path picker starts at `/` and is refused (navigate from the project instead), and an SSH project's terminals do not open over the relay.
- **A relay channel that names a project needs a row in `relay-project-scope.ts`.** The jail is keyed on channel class: any method named `githubIssues:*`, `board-log:*` or `projects.*` is refused on a scoped session unless that table can read its projectId. Add the row in the same change as the channel, or the verb is refused for every scoped guest (`relay-project-scope.test.ts` goes red and says so).

## Flow control: a paused phone stream is resumed by a drain sweep

`main/remote/host-service.ts`, `FLOW_SWEEP_MS`. `sendFrame` refuses and drops a frame once the relay socket holds more than 8 MB, and the host pauses the pty. A paused node-pty emits no `onData`, so the old resume-on-next-successful-send never fired and the phone's terminal froze until it detached. Do not reintroduce a chunk-driven resume, and give any new paused path the same trigger. It is the same drain-sweep pattern as `core/ui-sink-registry.ts`, whose self-paced sinks are never dropped at all.

- A 250 ms sweep, armed only while a stream is paused and cleared in `dropStream`/`closeAll`, waits for `bufferedAmount() <= 256 KB`, then runs capture, `OP.Snapshot*`, `setFlow(resume)`, in that order. The dropped frame desynced the phone; resuming first lets live output race the repaint.
- The repaint is not the attach snapshot's bytes. The phone feeds a snapshot into its emulator with no reset, over the old screen, so the resume payload (`resumeRepaintText`, `@shared/capture-paint`) is SGR reset, home, clear, then the screen with CRLF line endings (SwiftTerm runs convertEol off) and one trailing newline dropped, then the pane's cursor when `PtyManager.captureVisible` read it (else the attach's own capture, no cursor). The attach snapshot, painted into an empty emulator, stays the raw capture.
- A refused repaint retries with backoff (250 ms doubling to 10 s): a reconnecting relay reads 0 buffered but refuses every send, so no backoff means a tmux capture per tick.
- Output still queued after the pause is dropped, not streamed.
- An empty capture resumes without a repaint. This differs from `ui-sink-registry`'s keep-desynced rule, because staying paused here means staying frozen.
- `~/.nodeterm/relay.json` is written only when its content changes or the file is missing (`relay-advertise.ts`). The ~90 s listener cycle used to rewrite it identically (~960 times a day).

## The phone's chat screen verbs

`chat.page`, `chat.status`, `chat.send` and `agent.answer`, served by `host-service.ts` `handleChat` into `main/remote/host-chat.ts`. The spec and exact error strings are in [mobile-chat-view](mobile-chat-view.md) §3.2. Four rules a refactor must not undo:

1. **The phone sends only a node id.** cwd, account, agent and session are resolved from this machine's records (`WorkspaceStore.getNodeResolved` plus the mirror). The session id is asked of the renderer's agent-status store first (what ⌘M reads; after a restart a hook-fed id lives only there), and the mirror or minted id only as a fallback. The cwd rides only for a remote node with a known id, so a local known-but-dead id, or no id at all, reads nothing rather than claude's cwd-newest fallback (a stranger's session). An SSH-project node is read remote-only (`remoteOnly`): over its live pty's master, else its project's (`remoteTargetForNode`; an idle tab or any node after a restart has no pty, and resolving through the pty alone sent it to this machine's disk). A remote read that cannot happen is `unreadable` ("Could not read the transcript."), never `found:false`. Only chat-capable agents are served (`canChat(capabilityAgentId(agent))`).
2. **The send gate is the host mirror's, then the renderer's.** A send is refused first when the mirror says working, waiting or blocked, or holds a question or approval ticket (renderer state is transient after a reload). Then an IPC round trip (`host:chat-query` / `host:chat-reply`, sender-checked to the main window) is answered from the agent-status store and the ⌘M composer's `chatSendRefusal` at send time, plus "no held request". A renderer that does not answer fails closed: status is an error. `'refused'` (with a `reason`) means nothing was typed (no window, a gate, past `startBy`, or `busy`: one send per node in flight until it settles). A send whose outcome the desktop cannot confirm (no answer in time, or a `sendText` that rejected after starting, so it may or may not have been typed) is `'unconfirmed'`, never `'refused'`, which would invite the phone to resend and type the prompt twice. `ChatStatus` carries the mirror's view too (`hostRefuses`/`refusal`, `version: 1`): after a restart the window's `state` is null while the mirror may still hold a live dialog, and the phone must see the lock the send applies.
3. **Text is capped raw (64000), then stripped of ESC and C0/C1** (`\n` and `\t` kept), and rides `pty.sendText` (stdin into tmux, never argv). `'sent'` only for `sendText === true`.
4. **`agent.answer` is the desktop answer path.** It uses `answerHeldPermission` over the same `heldPermissionIoFor` (local fs or the SSH ControlMaster) and the in-process structured-ticket gate, and the `pendingId` must be this node's (a mirror approval ticket for it, or the renderer's `held.pendingId`), else `false` with no I/O and no answered event on the wrong node.

The `chat` dependency is optional at every hop, so a dropped hop compiles and ships the verbs inert ("not served"); `host-chat-wiring.test.ts` pins the chain at source level. The verbs are served only to an approved phone. Team Access relay guests never reach them (`relay-host.ts` serves no phone dialect). Server Edition: N/A (no phone relay; the bridge subscription is inert).

## Launch, scroll and keyed answers: the phone never types shell syntax

Relay-only hosts (every Windows pairing) have no SSH, and a Windows pane is pwsh or cmd, so the phone does not type shell syntax into a relay host.

- `pty.attach { launch: {agentId, sessionId?, cwd?, accountId?, permissionMode?} }` makes the host launch, only into a session the attach created, exactly once (`core/relay-launch.ts`, `PtyManager.prepareRelayAttach`). Every field is re-validated, cwd is jailed to the fs roots, cwd and account are folded into the spawn options of an unrecorded node (a recorded node keeps its records), and the line is built for the pane's real parser: `assembleResumeCommand` on POSIX, the trusted Windows planner when its resolver is wired, else only a dialect-neutral line.
- Reply `launched: true` means "type nothing", and it is promised only after a preflight build succeeded (`relayLaunchPreflight`; an unset `${env:...}` or a non-neutral custom line on a Windows pane answers `launched:false`, never a launch that silently never comes).
- The reply also says `paneShell: 'posix' | 'windows'`: whether a typed POSIX line is safe in that pane. That is not `hostPlatform`: a Windows desktop's SSH-project node runs on a POSIX host (not host-launched; the phone types as before). Without `launch` the reply is byte-identical.
- `pty.scroll` writes the wheel only on a tmux or mouse-requesting pane (`PtyManager.scrollRoute`). A session-host or plain stream's reply says `scroll:'local'` and its snapshot is the full buffer.
- Keyed answers ride `agent.key` (closed key set, host-side state plus an open-ask guard, hook reply first; an SSH-project node with no client held goes over its owner's ControlMaster or nowhere, never the local socket). Read acks ride `inbox.ack` (`applyPhoneReadAck`, the ack sweeper's body). Also `fs.browse` (home-jailed, dirs only) and `pty.capture`; `host.info` lists them. All additive: an old phone keeps its old path.

### A relay attach never decides where a session runs from what the phone sends

The phone's `pty.attach` goes through `PtyManager.prepareRelayAttach`, which routes an SSH project's node over its project's master or refuses it, and gives a local node the env the desktop would. Never spawn a session for a phone-named node id directly (`attachDetached` / `createDetached`): that is how an SSH node became a local shell in this machine's `$HOME`. The routing rules, resolver and refusal reasons are in [tmux-continuity](tmux-continuity.md) (a remote node is never spawned locally).

## Pins, revoke and consent

- **One relay pin store per role, and only the phone store admits anyone** (`main/remote/approved-devices.ts`). `phonePins` (`remote-approved-phones.json`) is what the standing host auto-approves from, silently, with the full phone vocabulary. `guestPins` (Team Access desktops we host) and `joinedHostPins` (hosts we joined) are records that nothing reads to admit; never write a desktop peer into `phonePins`. They used to be one file, so a host you once joined, or a guest whose seat you revoked, was auto-admitted as a phone. The pre-split `remote-approved-devices.json` is deleted at boot and nothing in it is carried over: nothing on this machine can tell its roles apart (the phone's relay box key is never sent at pairing, so agent.json cannot vouch for one), so every phone re-approves by SAS once.
- **Every revoke goes through `main/remote/peer-revoke.ts`:** unpin from the named role stores, then run every registered host killer (standing host pool including pending consent, the interactive `initRemoteHost` session, the Team Access `live` set). A revoke that knows only one host leaves the others serving. A new host that serves relay peers must `registerPeerSessionKiller`, or revoking a device leaves its shell open.
- **Phone "Remove"** (`pairing-service.revokeDevice`) revokes all phone pins and cuts all phone relay sessions, before the SSH key and the device entry go. It is all-phones because no box key maps to a device. A failure reports `local:false` and keeps the device listed to retry.
- **Standing phone consent belongs to the verified handshake, not the browse socket** (#819). A browse socket can close before the human clicks the SAS dialog. `core/phone-approval.ts` retains only the handshake-bound id and key for 120 seconds, at most 64 requests, one per key. Socket closure releases presence and transport but does not discard that bounded consent. Replacement, rejection, expiry and host stop clear the exact dialog id. Approval requires both the issued id and the displayed key (no key-only match, no mismatched-key fallback), consumes once, then persists before granting access. `remote:phone:approve` is raw owner-window Electron IPC, never a relay RPC. Keep request and reply outcomes distinct: stale request, failed pin save, missing IPC response (renderer rejection or timeout is explicitly unconfirmed), and saved-but-disconnected. SAS derivation and mutual trust verification are unchanged. Legacy interactive offers remain session-only, and Server Edition rejects standing phone approval as unsupported (it does not host this legacy relay path).
- **Pin and revoke writes are serialized.** Pin and revoke mutations use `updateApprovedDevices` to queue the whole read/modify/write in process, because a unique-temp atomic rename alone cannot prevent lost updates. All production writers must use it, so concurrent updates cannot lose approvals or resurrect revoked keys. Non-ENOENT reads and malformed JSON reject rather than overwrite unknown trust state. The queue is not a cross-process lock. A click accepted before host stop may finish its disk save, but must never open the now-closed session. See also [atomic-writes](atomic-writes.md).

## Phone pairing is platform-neutral

- New keys are stamped `nodeterm-mobile-<deviceId>` (`pairing-core.deviceCommentFor`). `filterAuthorizedKeys` matches both that and the legacy `nodeterm-ios-<deviceId>` (`deviceCommentsFor`), because every iPhone paired before Android existed carries the old stamp. Drop the legacy leg and "Remove" reports a phone removed while its SSH key stays live.
- The device name is what the phone sends (Android sends one), sanitized to one line of at most 64 code points. With none it is `'Phone'`, except the iOS app, which has never sent a name, is recognised by its fixed key comment `nodeterm-ios` and keeps `'iPhone'`.
- Store links go through `renderer/lib/links.ts` `mobileStoreLinks()`. The Play link is hidden by the single `ANDROID_APP_PUBLISHED` flag until the listing exists, and `mobileStore.guard.test.ts` refuses a direct store URL anywhere else in the renderer.
- `LicenseSource` includes `'google'` (a Play purchase bridged from the phone, `google:<orderId>`), with its own `licenseCopy` sentence. `settings.mobileLiveActivities` keeps its key; the UI says "Live updates on phone".

## A Windows desktop pairs relay-only

No SSH key is installed on a Windows desktop, and it must not be "fixed" by writing one. The phone's direct-SSH path is POSIX sh plus tmux end to end (nodeterm-ios `HostCommands`, `TmuxBinary`, the typed `tmux new-session -A` attach, workspace paths with no `%APPDATA%` candidate). Windows OpenSSH hands out `cmd.exe`, and sessions live in the session host, which nothing on the phone can attach to over SSH.

- On win32 `createPairingService` installs no key, the QR carries `"ssh":false`, the QR is gated on the relay instead of sshd (`shared/pairing-gate.ts`), and a failed relay mint pairs nothing (502 to the phone, `reason:'relay-failed'` to the UI) instead of the SSH platforms' LAN-only degrade.
- A key sshd accepts makes things worse, not better: the phone tries SSH before the relay, so a working key pins it to a path that cannot work, where a rejected one lets it fall through. Do not install the key into `administrators_authorized_keys`.
- Issue #758's `administrators_authorized_keys` rule is detected (`main/windows-ssh-keys.ts`) only to explain the missing key. Revoke still sweeps that file in place: a temp plus rename would swap its Administrators+SYSTEM ACL for the directory's, and sshd would then refuse every admin key in it.
- Relay attach on Windows rests on the session host being packaged (#575, shipped by #579). Without that bundle `pty.attach` spawns a new plain shell instead of joining the node's session, while `sessionExists` still answers "warm". See [windows-session-host](windows-session-host.md).
