# Canvas panels: Explorer, Source Control, Settings page

The side and modal panels around the canvas: the Explorer drawer (`ExplorerPanel.tsx`), Source Control (`SourceControlPanel.tsx`, `src/core/git-service.ts`), the Settings page (`SettingsPage.tsx`), plus the Shortcuts panel and welcome screen. Worktree-scoped Source Control is in [worktrees](worktrees.md); the shortcuts inventory is in [keybindings](keybindings.md).

## Explorer

`ExplorerPanel.tsx` (🗂 / ⌘⇧E): a lazy file tree of the active project `cwd` (`fs:list`). Click a file to open an editor node; right-click offers Copy Path, Reveal, New File... and New Folder... (an empty-area right-click targets the root; SSH projects create on the host). The canvas pane right-click and ⌘K also expose New file..., which creates under the project cwd and opens an editor node. These use `mkdir` and `exists`, added to `FsApi` / `SshFsApi` across desktop, server and SSH (`core/fs-ops.ts`, `main/ssh-fs.ts`).

- **Relay tabs are not degraded.** A relay tab's `fs` routes through `bridge/relay-api.ts` (`fs: files.fs`) to `buildFilesApi`'s `IPC.fsMkdir` / `IPC.fsExists` (`bridge/ws-bridge.ts`) to `core/fs-handlers.ts`, and on to the real `fsOps.makeDir` / `fsOps.pathExists` on the peer's core, so both verbs are live there. What genuinely still lacks them is the legacy phone vocabulary (`main/remote/host-service.ts`): its `handleFs` switches on `fs.list` / `read` / `readBinary` / `write` and nothing else, so `fs.mkdir` / `fs.exists` fall through to the dispatcher's `Unknown method` rejection rather than degrading to `false`. That is a different dispatch path (`relay-host.ts`) from the relay tab above.
- **Expanded dirs persist per project** across drawer close and app restart (`state/explorer.ts` zustand store, localStorage `nodeterm.explorerExpanded`).
- **Pin.** The header pin docks the drawer like the sessions sidebar (`lib/explorerPin.ts`, `nodeterm.explorerPinned`, default off). Overlay click-outside closes the modal only, and a pinned overlay is `pointer-events: none` so it cannot steal canvas clicks. × is a transient hide and does not clear the pin. The pinned z-index is 26 so the tree stays visible on the kanban board with the controls cluster. A pinned panel also participates in camera framing (see the pinned-panel exception in [canvas camera](canvas-camera.md)).
- Surfaces: Desktop and Server Edition (personal `localStorage`). Mobile: N/A, no explorer there. Source Control stays a modal.

## Source Control

`src/core/git-service.ts` (system `git` and `gh`) and `SourceControlPanel.tsx` (⎇).

- Features: file-level stage/unstage (+/-), discard, click a file to open a diff node, branch switch/create, commit (message box at top) with push / sync / publish, a gh sign-in banner (runs `gh auth login` in a new terminal via `initialCommand`), and recent commits.
- **AI commit message** (✦ Generate) and **AI terminal naming** both use `main/commit-message.ts`: a bring-your-own local agent CLI (claude/codex/custom) spawned read-only on the staged diff or captured terminal output. There is no built-in model; the agent and extra prompt are set in Settings.
- The panel operates on a selected scope, not on the project cwd (see [worktrees](worktrees.md)).
- **Open latency and reopen.** `status()` must never await `gh auth status`: it hits the GitHub API (about 700 ms) and used to hold the panel's first paint hostage. `ghAuthedSwr()` returns the cached answer and refreshes in the background; the accurate `ghAuthed()` is still awaited on the publish flow. Status and history live in the per-cwd `state/scmCache.ts` store (same pattern as `scmDraft`), so the close/reopen cycle paints the last-known data instantly while the mount refresh replaces it silently. Do not move them back into component `useState`.
- **Branch observations** (`state/gitBranches.ts`) are shared by Source refreshes, Sessions project headers and existing worktree status polls. They are scoped by GitApi identity + exact cwd + SSH project id, never persisted, and latest-started reads win over late responses. Sessions resolves each project's owning session (including background projects); its header reads the project cwd, while a group header reads only its worktree path. No new timer: sidebar mount/reopen/cwd changes read local checkouts once, Source operations refresh as before, and worktrees keep their existing gated cadence. SSH headers only observe Source refreshes, because background SSH connections are not git-routable. Local header probes also skip a cwd claimed by the active SSH route. The branch projection does not replace worktree staleness/ownership decisions or SCM history.

## Settings page

`SettingsPage.tsx` (⚙ / ⌘,): font/cursor (live to xterm and Monaco), default shell, grid and snap, default node size, pan-hover delay, double-click focus, accent, tmux on/scrollback, commit agent, `seenShortcuts`.

- **Default node size** is one row with a kind picker. Terminal/agent is the `defaultNodeWidth` / `defaultNodeHeight` pair, clamped in `terminalNodeSize()`. Every other kind the add menus create is an optional entry in `defaultNodeSizes`, resolved by `defaultNodeSize(kind)` in `state/workspace.ts` through `@shared/default-node-size`, which clamps hand edits to the kind's `NODE_MIN_SIZES` and 2400x1600. New factories must place through `placeSized`, not a literal `*_SIZE`, or the setting silently stops applying to that kind. The agent `settings` verb exposes only the terminal pair.
- **Every section is mounted whenever Settings is open.** An inactive one returns null from `SettingsSection`, but its hooks and the whole render body above that return still run. So a throw in a section the user never navigated to blanks the entire page. #1090 (0.4.0) was `GitHubIssuesSection` calling `dispatchBindingFor` during render, a closure over a `const repository` declared about 140 lines lower (below the early returns): a TDZ ReferenceError on every Settings open once dispatch was switched on for the active project. `tsc` does not flag a closure that reads a later `const`, only a direct read, so declare anything a render-time helper closes over above the helper. Each section is wrapped in `SettingsSectionBoundary`, which contains a throw to that section (fallback shown only while it is the viewed section). Keep new sections inside one.
- **A setting read at mount reads the default, not the user's.** `useSettings` starts on `DEFAULT_SETTINGS` and hydrates from disk asynchronously, while `<Canvas />` is mounted before that lands. A `useState(() => settings.foo ? ...)` initializer therefore reads the shipped default and never looks again, so an opt-in feature ships inert with a green suite and no error anywhere. Gate on `hydrated` (the first-launch consent dialog and `settings.rememberCanvasLock` are the worked examples). If the same effect also writes, latch its first run: otherwise switching the setting on mid-session applies stored state to whatever the user is doing right then, which is a different feature from the one they asked for.

## Shortcuts and welcome

- **Shortcuts** (`ShortcutsPanel.tsx`, ? / ⌘/): shown once on first launch (`seenShortcuts`). It is derived from the keybinding registry, never hand-listed; see [keybindings](keybindings.md).
- **Welcome** (`WelcomeScreen.tsx`): shown when no projects exist.
